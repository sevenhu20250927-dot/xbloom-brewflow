本目录保存xBloom BrewFlow的设计目标和实际进度，供维护者与接手Agent使用。更新日期：2026-11-12（Asia/Shanghai）。这不是冲煮入口；实际使用技能从根目录[SKILL.md](../SKILL.md)开始。

| 文档 | 回答什么 | 何时更新 |
| --- | --- | --- |
| [设计目标](GOALS.md) | 为什么做、已经确认的要求、完成应表现为什么、哪些实现仍待设计 | 需求或明确决定改变时 |
| [开发状态](STATUS.md) | 当前实现和证据、剩余缺口、建议下一步、未验证事项 | 每次开发交接前 |

目标与进度分开，避免把“想实现”写成“已经实现”；本页集中入口与续接操作，换机器不必恢复此前聊天。具体协议、参数和知识合同继续引用原文件，不在这里复制第二套。

## 换机器继续

代码与这些文档以[GitHub仓库](https://github.com/sevenhu20250927-dot/xbloom-brewflow)为共享入口，不依赖原testCoffee项目、原机器的绝对路径或SQLite服务。

首次在新机器选择一个开发目录后：

```sh
git clone https://github.com/sevenhu20250927-dot/xbloom-brewflow.git
cd xbloom-brewflow
git status --short --branch
```

已有副本先检查当前分支和未提交内容，再获取远端变化；不要覆盖另一台机器尚未提交的修改。开始具体开发时使用`codex/`前缀的任务分支。换机器前提交并按当次授权推送；GitHub不会自动同步未提交的本地文件。

1. 先读[目标](GOALS.md)，再读[状态](STATUS.md)，核对实际Git分支／提交和文件；文档里的基线日期不是永远最新的状态。
2. 根据状态中给出的代码入口确认待做范围。状态为“建议”的内容不等于用户已批准全部实现。
3. Python环境按[安装说明](../README.md#安装)在新机器重建；不复制`.venv`、设备地址或本机权限。源码开发可跨机器，当前BLE运行支持与实机验证范围仍以README为准。
4. 注意正在修改的开发副本与Agent已安装的技能可能不是同一目录。验证时显式指定当前副本的脚本，更新已安装技能时保留个人工作数据。
5. 结束时更新`STATUS.md`中的状态、证据、未解决问题和下一步；需求发生变化才修改`GOALS.md`。只把实际执行过的验证记为通过。

可将下面这段交给另一台机器的Agent：

> 请先读 development/README.md、GOALS.md 和 STATUS.md，并检查Git状态。说明当前目标、已实现与未验证部分，以及建议接续的最小任务。不要把待办当成已实现，也不要因历史许可启动咖啡机。

## 数据与执行边界

- 随包`knowledge/`是已经公开的历史种子数据；新用户的`CoffeeWorkspace`保存自己的杯次、偏好和经验。发布者已允许公开自己的冲煮资料，不因此推定其他使用者也同意公开。
- 本仓库不依赖原库存数据库。新记录若需进入公开冷启动库，应显式整理来源、关联和变化，再作为普通代码变更审阅；目前没有自动同步或增量导入服务。
- 启动真实研磨、出水或冲煮，仍需对当次审核配方的明确开始指令。开发交接不是设备授权。
- 测试、模型调用、提交和推送遵循当前环境与本次用户授权；此文档不授予后续任务无限权限。历史97项测试通过仅是已记录证据。
