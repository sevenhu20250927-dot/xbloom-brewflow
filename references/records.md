# 工作目录与证据

随包`knowledge/`是已公开的历史参考；当前用户新增记录另存，不在历史源文件上覆盖。最小目录按豆子与杯次组织，由使用者选择位置。例如：

```text
CoffeeWorkspace/
  preferences.md                 有实际偏好时才创建
  beans/<豆子批次>/<杯次>/
    record.md                    条件、参照、方案审核、反馈与后续
    recipe-v1.json               机器执行参数；修订另存v2
    logs/
      <会话>.jsonl               每次尝试独立追加，不手工修改
      reports/<会话>.html/.svg   从日志重建
      index.html                 本杯全部尝试及品饮记录入口
```

总账命令可对`CoffeeWorkspace/beans`运行，递归汇总所有杯次。它只扫描显式目录下的普通文件，不跟随符号链接，不查Git其他worktree。重新生成：

```sh
"$BREW_PY" "$SKILL_ROOT/scripts/xbloom.py" history "$COFFEE_WORK/beans"
```

这份总体index由Agent在每泡结束、反馈写入后刷新并给用户链接；程序自动生成的是本次`--output`目录index。重复重建不增加冲煮次数。重试分别展示，但不能把同一杯的两次尝试解释成两个满意样本。

## record.md必须能回答

- 豆子批次、处理法、烘焙日期、保存、器具、水、品饮者：已知与未知分别记。
- 为什么选该配方：近邻参数与反馈、差异、来源、采用与放弃的理由。
- 哪个版本得到审核，谁在何时发出开始／重试指令，日志路径与配方指纹是什么。
- 实际观察到哪些阶段；异常、未收到的数据和人工核对是什么。
- 各品饮者原话、温区、评分量表、希望改善与保留什么；修方另存版本。

记录无需复制大段JSONL。总账寻找日志同目录的`record.md`，或标准布局中`logs/`上一级的`record.md`，以转义文本附在详情页；不会把记录里的HTML当成脚本执行。多次尝试共享同杯记录，必须在文中注明哪条反馈属于实际喝到的杯子。

## 不能混用的量

配方温度／RPM／研磨／粉量是设定，通知是机器回报，人工称量与屏显是独立观察。原始machine_info的研磨值可能是旧快照，不能用它覆盖目标值。

报告时间轴始于首段注水；40512作为结束候选，缺失时可以用ready并注明来源。它们都是主机接收间隔，不能声称是机器屏显计时或最后一滴。自动completion保持unconfirmed；用户看见屏幕或末滴后将原话写入record.md。

液重使用回idle前（或截止前）的末次有效值，不能保证稳态或实际成品重量。取杯导致下降时保存原始值与用户指定采纳值及理由，不把峰值自动当正确值。报告只排除其明确规则下的孤立向上尖峰，原始样本保留。

`water_g`是按来源解码的出水计数，单位仍需独立校准；蓝柱为杯中液重变化率，不是机器注水流速。没有折光仪等测量时不报告实测TDS／EY。

## 经验积累

有可复用提案时再创建`knowledge/raw/`，引用支持杯和反例、限定条件，不重复拷贝所有杯次。审核人明确认可具体结论后才能进入`knowledge/certificated/`。初次安装不创建空知识层或预填“验证成功”。反馈和因果主张分开；不同品饮者各自保留，重复点单或沉默不算好评。
