# 杯次、对比与知识记录

这些是Markdown记录合同，供Agent书写和实际审核人review，不是机器强制校验的Schema。按实际资料填写，未知写未知；“不适用”“未测”“未执行”“没有反馈”不能写成0。

## 同豆目录

个人工作目录的`beans/<豆子批次>/`的标识优先沿用库存唯一ID；没有则使用可辨认名称，并在索引列出批次，近似名称不自动合并。每个新杯次用不冲突的时间或既有run标识建目录；同一杯重试写在原杯次里并区分每次启动，不生成多次满意样本。旧记录保留原路径，索引链接到source-snapshot或imports。

本发布包新杯次使用`record.md`（随包历史保留`记录.md`）作为一个完整入口。被审阅后的方案修订另存`方案-v2.md`等，旧版不覆盖；审核引用具体版本。原日志、实际recipe与报告继续使用原执行器输出，用链接关联。跨杯的`对比-<杯次A>-<杯次B>.md`放在同豆目录；多杯比较列全基准，不自行选掉不利样本。

## 杯次记录所需内容

| 部分 | 必须表达的内容 |
| --- | --- |
| 条件与来源 | 豆名、批次、豆龄／烘焙日期、保存、器具、磨豆机、水等已知条件；品饮者；基准杯；原始文件引用。缺失不补齐 |
| 原话与目标 | 热／温／凉、具体感受、个人喜好，想改善什么和保留什么；反馈原文不混入AI归因 |
| 决策依据 | 查过哪些知识与案例，raw或certificated身份、适用与冲突；候选解释及动作、采用／未采用理由 |
| 参数变化 | 参数／段位／前值／后值／单位／主改动或联动。粉量、过粉水、绕流分别列，比例派生；全部差异展开 |
| 预期与观察点 | 影响的感官项、期待方向、可能代价；需要核对的过程数据；不把预期写成结果 |
| 审核与执行 | 方案版本、真实审核答复与时间；开始指令另记；实际配方与计划差异、日志和报告、失败或异常 |
| 反馈与后续 | 原话、品饮者和温区；未反馈保留空缺；对比和知识提案链接 |

感官观察保留原反馈卡六维度及入口／中段／余韵关系，10项案例索引可辅助检索。风味名称、正负评价、原因解释、温区是不同内容，不把所有“薄”当成同一症状。

## 跨杯对比所需内容

- 引用基准与新杯，说明比较目的。
- 逐项列配方变化和已知非配方变化，包括批次、豆龄、设备、品饮者；未知项单列。
- 各杯原话及出处、机器数据及口径；没有统一测量时只作定性比较。
- 哪些预期兑现、哪些代价出现、哪些无法判断。
- 结论限于观察、组合效果还是待验证因果；指出下一步能区分的疑问，不自动冲下一杯。

## 知识提案所需内容

一个文件对应一条可审核陈述：

| 部分 | 用途 |
| --- | --- |
| 陈述与适用范围 | 说明什么条件下哪个动作可能影响哪个感受；保存人、豆、设备边界，避免无限泛化 |
| 依据 | 原始概念来源、支持／反驳杯次及对应对比；来源相互矛盾时保留两者 |
| 观察与假设 | 明确实际反馈是什么、因果解释是什么、没有验证的部分是什么 |
| 审核 | 待审；或真实审核人、时间、答复、获认可的确切陈述与范围；没有发生不填写认可 |
| 后续状态 | 反例与待复核原因、范围修订及历史决定。不要用覆盖正文消除旧错误 |

只说“好喝”可进入个人日志，但不足以确认“研磨提高了甜感”。同一杯有两个品饮者，分别保留反馈，不当作两次独立冲煮实验。文件日期只用于追溯，不代替来源可信性。
